一、怎么用这份清单
======================================================================

【1. 适用范围与两个版本位】

这份清单测的是 dsh-cursor-modes 这个包，不是实例。同一个包在两个实例上版本不同，
条目按两种标记区分：

  （无标记）     归档 0.2.6 = 3080 现状 = 4000 除下列五处外的主体代码。两实例都应成立。
  [0.2.7·仅4000] 只在 4000（0.2.7）上有对应实现；3080/归档尚无此代码，按现状记 NA，
                 不要因为 3080 不通过就判失败。

0.2.6 与 0.2.7 的实测差异（用 git diff 与文件哈希核过）：

  lib/client.js     0.2.7 多出 subagent-panel 区域（1730-2058 行），并删掉 PlanCard 读会话 todos
  lib/planfile.js   0.2.7 的 readPlanDispatch 额外返回 frontmatter 的 todos
  lib/prompts.js    0.2.7 把「当前模式由最新一条用户消息里的标记决定」改为
                    「由最新的 runtime-context 快照决定，该快照在压缩后重建」
  package.json      version 0.2.6 -> 0.2.7
  其余 lib 文件（index/plan/state/multi/gate/switch/routes/build/settings/planfile 以外的 18 个）
  与 routes.js、build.js、gate.js、plan.js、state.js 等全部哈希相同。

【2. 跑的顺序】

先跑 S0，再按 A -> I 走。CM-D 要真实派子代理，最贵也最容易留下残留会话，放到计划类之后。

  S0 自检脚本
     在实例插件体目录里依次执行（不要在本归档目录跑，理由见 CM-H-10）：
       cd “<实例>\profiles\web\.dsh-launcher-plugin-bodies\dsh-cursor-modes”
       node self-check-gate.mjs
       node self-check-policy.mjs
       node self-check-runtime.mjs
       node self-check-bridge.mjs
       node self-check-settings-ui.mjs
       node self-check-subagent-todos.mjs
       node self-check-fold.mjs          （Layer 2 现状是红的，见 CM-H-05 与已知问题 3）

  然后 CM-A（模式系统）-> CM-B（模式规则）-> CM-C（计划模式）-> CM-D（多任务）
      -> CM-E（工具）-> CM-F（子代理界面）-> CM-G（设置与闸门）-> CM-H（自检复核）
      -> CM-I（边界与流程）。

  每条之间新开一个会话，或至少确认 chip 上没有遗留的待定选择（见 CM-A-02）；
  同一条目在两实例各跑一遍，记录里写清实例号与版本号。

【3. 怎么触发（三种通道，条目里会指名用哪一种）】

  UI 通道     点界面：composer 左侧的模式 chip、计划卡片的两个 Build 按钮、
              设置 -> 插件 里的「Cursor Plan 委派门禁」标签页。
  消息通道    在输入框发一句话（模式提交只在「真实用户消息被 claim」那一刻发生）。
  接口通道    loopback POST/GET，例如：
                Invoke-RestMethod -Method Post -ContentType application/json `
                  -Uri http://127.0.0.1:4000/api/dsh-cursor-modes/switch/vocabulary -Body '{}'
              页面内 fetch 不需要额外头；命令行若被拒（401/403 且 body 里的 code 不是
              loopback-only），说明该实例要求 token，从 launcher.out.log 的 dsh web: 行取 token 补上。
              所有这些桥只接受 loopback 来源，这是设计不是故障（见 CM-G-08）。

【4. 判定标准】

  一条判 PASS 的条件：操作能重复做到；「期望」里列的每一项都观察到了（原文文字、DOM 属性、
  JSON 字段、日志整行、文件 frontmatter、进程内计数），而不是「界面看起来正常」。
  只对上一部分的判 PARTIAL，写明哪一项没对上。
  稳定复现的对不上判 FAIL。跑不动（缺依赖、实例没起）判 BLOCKED，不算失败。
  期望里的精确字符串（例如 “Granted: 5 more calls in this stretch.”）逐字比对；
  文案是模型的输入，改一个字就是行为变更。

【5. 失败怎么记】

  每条失败照下面的模板记一行，写在记录文件里，不要改本文件：

    [编号] FAIL | 实例 4000 或 3080 | 版本 x.y.z | 时间 | 会话 id
      现象：看到了什么（原文/DOM 片段/JSON，截图给路径）
      对照：源码 file:line 说的应该是什么
      复现：N/N 次

  硬规矩：本清单只做记录。发现缺陷不改代码、不改配置、不重启实例；
  任何修复都走「4000 改 -> 4000 重启验证 -> 才允许上 3080 与归档」的顺序（见 CM-I-03）。

======================================================================
十一、已知问题 / 待观察
======================================================================

这一节只记录，不修。每条都写了「现在是什么样」和「看哪里」，供下次动手时定位。

K1. 计划卡片的清单绑定：两个版本各有一半问题
   现在（归档 0.2.6 = 3080）：卡片的清单读的是会话 todos 投影，投影为空才退回 create_plan 的参数快照
   （lib/client.js:120,130）。因此改 .plan.md 的 frontmatter 不会改变卡片；而会话投影是内核的，
   回合结束就被清，重开历史会话时看到的是当初的参数快照。
   现在（4000 · 0.2.7）：反过来只认文件 frontmatter（4000 版 lib/client.js:113-120,145-163），改文件
   立即反映，代价是卡片不再随回合实时打勾 —— 代码注释自己写着「the card no longer ticks while a
   turn works」（同处 :118-120），把「执行进度写回文件」留成了后续。
   为什么要单列：这是用户点过名的缺陷，且修法在两版之间换过一次方向，别把旧结论套到新版本上。
   相关条目：CM-C-06（清单渲染）、CM-C-11（派发戳）、CM-C-14（改 .plan.md 刷新）。

K2. 面板折叠只落地到 4000（0.2.7），归档与 3080 还是皮肤在管
   现状：0.2.7（仅 4000）新增 lib/client.js 的 subagent-panel 区域（1730-2058 行），用
   [data-dcm-collapsed] + .dcm-expand-more + window.__dcmPanelStats 自己管折叠；皮肤
   dsh-colombia-skin 0.2.2 里那张 dcs-expand-more 卡（皮肤 lib/client.js:495,640-700,777）仍然在，
   没有同步删除。归档 0.2.6 完全没有这段代码（归档 lib/client.js 只到 1825 行，subagent-copy 后
   直接是 index 区域）。
   待观察：3080 一旦升到 0.2.7，插件与皮肤会各画一张「展开更多」卡，谁赢取决于 CSS 具体度
   （0.2.7 的注释说皮肤用 body .dcm-expand-more 压过插件基线表，:1753-1758），但没人在 3080 上
   验过两张卡并存时会不会叠出两个按钮。升版前必须先确认皮肤侧是否同步摘掉。
   迁移落地后要更新的条目：CM-F-05（负断言会失效）、CM-F-06/07/08（标记从「仅 4000」改成通用）、
   CM-I-04（版本对齐）。注意目前 CM-F-05 是**故意写成现在这样**的，不要当成漏测。

K3. self-check-fold 的 Layer 2 与注释互相矛盾（现状红）
   注释说 Layer 2 要求「新折叠与冻结基线零不一致」（self-check-fold.mjs:14-17,484-485）；
   但冻结基线 tools/legacy-fold.mjs 只认 cursorPlan/state 与 mode/selected（:80,:142），而 0.2.3 起
   唯一的写入名是 plugin:cursormodes/state（lib/projection.js:66），基线看不见它 -> 折出 default。
   2026-10-29 在 4000 的实测：223 个有模式事件的会话里 33 个不一致，全部是 new=plan/multi、
   legacy=default（_reports\plandoc\self-check-fold.mjs.log:31-47）。
   两边都没错，是「冻结」与「改写入名」这两件事同时成立后没有重新对齐：要么基线补一层 plugin:
   前缀剥离（但那就不是冻结基线了），要么把 Layer 2 的期望改成「新名记录由基线跳过，只比对老名」，
   要么在扫描时把新记录翻译成老记录再交给基线。
   相关条目：CM-H-05。

K4. routes.js 文件头说 eight，实际是 9 条，且有一条不是 POST
   文件头写 “The plugin's whole HTTP surface: eight exact POST routes under one prefix”
   （lib/routes.js:2），列举里 8 条，但正文还有一条 plan-state（GET，lib/build.js:34,298-300），
   总计 9 条。self-check-bridge 的断言表按名字比对，所以测试不会因此变红 —— 只有读注释的人会数错。
   相关条目：CM-I-07。

K5. 3080 的闸门配置里有四个在 llm 后端下不生效的字段
   3080 的 cordis.patch.yml:407-417 写着 backend: llm、model: jev-latest、
   baseUrl: http://127.0.0.1:7899/api/v1、allowConfidence: 0.8、workReject: 0.5。
   但 llm 分支用的是 gateDelegation 的 decideLlmVerdict（lib/delegation-gate.js:362-364,227-248），
   model/baseUrl 只在 jev 分支被读（lib/plan.js:189-191），两个阈值也只参与 decideVerdict 的
   数值判定（:105-129）。所以这四个值现在全是「写着但不生效」。
   风险：下次有人想调严一点，改 workReject 不会有任何效果，会以为是 bug。要么在卡片上加一句
   「当前后端不读这些字段」，要么把无效字段从配置里摘掉。
   相关条目：CM-G-05、CM-G-06、CM-B-08 以外的判定类条目。

K6. 0.2.6 的模式规则文案与实现不符（0.2.7 已改，归档/3080 未跟）
   归档 lib/prompts.js:72 写「当前模式由最新一条用户消息里的 <当前模式> 标记决定」，但标记实际
   由 runtime-context 快照携带，而快照在上下文变化或压缩后会重建、可能出现在若干轮之前
   （lib/index.js:227-237）。旧文案会把「最新用户消息里没有标记」误判成 default。
   4000 的 0.2.7 已改成「由最新的 runtime-context 快照决定，该快照在压缩后重建」（4000 版
   lib/prompts.js:72 及三处小节），这正好是 CM-B-09 要测的东西。归档回档时应把这处一并带回。

K7. cursor-plan.js 里有四个已无调用者的遗留导出，注释仍在描述它们
   grep 结果（只算 .js 运行时）：foldCursorPlan、cursorPlanView、planNoticeId、parseModeArg 在

   restores the mode from it」，指的是一个已经被 projection.js 取代的函数。
   风险：下次有人以为改 foldCursorPlan 会改行为，改完没有任何效果。
   相关条目：CM-H-05（冻结副本才是被测对象）。

K8. locale/*.json 只是镜像，运行时只读 client.js 内联字典
   lib/client.js:1534-1652 内联了 zh/en 两本字典并注册；locale/zh.json 与 locale/en.json 是给
   self-check-settings-ui 断言「逐键相等」用的镜像（self-check-settings-ui.mjs:501-522）。
   也就是说：只改 locale/*.json 界面不会有任何变化，但自检会红；只改内联字典则自检也会红，
   因为镜像对不上。两处必须同改。这一点在任何注释里都没写。

K9. 计划文件名按 UTF-16 码元截断，可能截出半个代理对
   lib/planfile.js:45-55 的 sanitizeName 用 slice(0, 100) 截断，是 code unit 而不是码点；名字里
   有 emoji 或扩展区汉字时，第 100 个码元可能落在代理对中间，产出替换字符或非法文件名。
   代码自己标了 ponytail（:37-42），承认了这段的粗糙度。属低概率、可复现要特意构造。
   相关条目：CM-C-02（命名规则）。

K10. 重复派发没有服务端闸门，派发戳只用于展示
   build 路由的 409 只表示「该会话没有活的 agent」（lib/build.js:241-245 -> session-not-live），
   并不检查计划是否已经派发过；frontmatter 里的 dispatched 是**展示用**的戳（markPlanDispatched，
   lib/planfile.js:170-184），不参与任何判断。
   所以：UI 路径是安全的（卡片在 plan-state 返回前不渲染按钮，已派发则渲染 Dispatched，
   lib/client.js:139,250-255），但直接 POST /build 两次会给会话塞两条「The user clicked …」消息，
   而卡片仍显示 Dispatched。
   附带风险：markPlanDispatched 用 yaml.load + yaml.dump 重写 frontmatter（:171-182），用户在头部
   手写的 YAML 注释会被丢掉；键顺序与值内容不变。
   相关条目：CM-C-11、CM-C-12。
